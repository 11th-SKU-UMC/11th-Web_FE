## 필수 미션

### 1. ORM 기반 Entity 및 Repository 구현

3주차에서 Raw SQL로 구현했던 도서 API를 Spring Data JPA 기반으로 리팩터링하였다.

`Book`과 `Category`를 각각 Entity로 구성하고, 하나의 Category에 여러 Book이 속할 수 있도록 `@ManyToOne` 관계를 적용하였다. 또한 DB의 `book_id`, `category_id`와 Java의 필드명을 명시적으로 매핑하였다.

`BookRepository`는 `JpaRepository<Book, Long>`을 상속하여 기본적인 조회 및 저장 기능을 Repository에서 처리하도록 구성하였다.

```java
public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findAllByOrderByBookIdDesc();
}
```

### 2. GET /books 구현

Repository에서 도서 목록을 최신 등록순으로 조회하고, Service에서 Entity를 `BookResponse` DTO로 변환한 후 Controller에서 응답하도록 구현하였다.

응답에는 다음 정보를 포함하였다.

* bookId
* title
* description
* categoryName
* isAvailable

Postman에서 `GET /books` 요청을 보내 정상적으로 도서 목록이 반환되는 것을 확인하였다.

### 3. POST /books 구현

`categoryId`, `title`, `description`을 Request DTO로 전달받아 새로운 도서를 등록하도록 구현하였다.

요청으로 전달받은 `categoryId`를 먼저 Category Repository에서 조회하고, 존재하는 Category인 경우에만 `Book` Entity를 생성하여 저장하도록 처리하였다.

```java
@Transactional
public BookResponse createBook(CreateBookRequest request) {
    Category category = categoryRepository.findById(request.categoryId())
            .orElseThrow(() ->
                    new IllegalArgumentException("존재하지 않는 카테고리입니다."));

    Book book = new Book(
            category,
            request.title(),
            request.description()
    );

    return BookResponse.from(bookRepository.save(book));
}
```

Controller에서는 `@Valid`와 `@ResponseStatus(HttpStatus.CREATED)`를 적용하여 요청 검증과 `201 Created` 응답을 처리하였다.

Postman에서 정상적인 데이터를 전달했을 때 새로운 도서가 등록되고 `201 Created`가 반환되는 것을 확인하였다.

### 4. DTO 검증 및 예외 처리

Entity를 API 응답에 직접 사용하지 않고 Request DTO와 Response DTO를 분리하였다.

제목은 빈 값이 들어오지 않도록 `@NotBlank`를 적용하고 최대 100자까지 입력할 수 있도록 `@Size(max = 100)`을 적용하였다. `categoryId`에는 `@NotNull`을 적용하였다.

또한 존재하지 않는 `categoryId`를 전달했을 경우 도서가 저장되지 않고 오류가 발생하는 것을 확인하였다.

### 5. Raw SQL에서 ORM으로 변경한 점

3주차에는 SQL 문자열과 파라미터를 직접 작성하여 DB를 조회하고 데이터를 저장했지만, 이번 주차에는 Entity와 Repository를 사용하여 DB 작업을 수행하도록 변경하였다.

SQL을 직접 작성하는 코드가 줄어들고 Repository의 메서드를 통해 조회 목적을 코드에서 더 명확하게 표현할 수 있었다.

또한 Entity와 DTO를 분리하여 DB 구조와 API에서 주고받는 데이터를 구분할 수 있었고, DTO 검증을 통해 잘못된 요청이 Service 로직까지 전달되는 것을 방지하였다.

### 6. 최종 검증

Postman을 이용하여 `GET /books`의 정상 응답, `POST /books`의 `201 Created` 응답, 빈 제목 및 존재하지 않는 Category를 전달했을 때의 오류 응답을 확인하였으며, 모든 결과가 요구사항에 맞게 동작하는 것을 확인하였다.
